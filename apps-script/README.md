# Private staff match decision log

The public matching tool remains unchanged. This Google-hosted version uses the same `index.html` scoring code and adds a private, automatically saved history to the existing team Google Sheet. It does not assign mentors in the app or import the existing admin roster.

## Files

- `Code.gs`: staff access checks and append-only decision events in Google Sheets.
- `client.js`: decision entry, required reason, confirmed assignment, history, and save/retry messages.
- `build.cjs`: assembles the staff page from the existing scoring tool plus the log interface.
- `Index.html`: generated by the build, deliberately excluded from Git.
- `appsscript.json`: authenticated Google deployment configuration, with no credentials or private file IDs.

Build with `node apps-script/build.cjs`. Run `node tests/mentor-form.test.cjs`, `node tests/match-log.test.cjs`, and `node tests/match-log-client.test.cjs`.

## Workflow

Staff open the Google-hosted page with an authorized Google account and load the teen/mentor answer files. Prior log history loads automatically. Each teen has a chosen-mentor selector and a required reason. Record decision writes a pending assignment. Staff make the actual assignment in the admin portal and then confirm it in the log. Neither action is performed automatically in the admin portal.

Corrections append new events and keep earlier reasons, mentor choices, timestamps, staff identity, and score snapshots. Existing decisions flag teens reappearing in a waiting queue. The log cannot detect reassignments that happen only in the admin portal and remains separate from its authoritative roster.

A lost response is retried with the same identifier to prevent duplicate rows. Concurrent corrections require the latest event identifier and are rejected if another staff member changed the decision. Unsaved form input stays in the open page and closing it warns of unresolved work. Browser drafts are not stored permanently; refresh or closing can still lose unrecorded input. A saved confirmation, followed by history readback, is the completion checkpoint.

## Setup in the existing spreadsheet

1. Open the existing log spreadsheet under the intended company account. Choose Extensions > Apps Script. Use this bound project; do not create another spreadsheet.
2. Copy `Code.gs` into the script's Code file. Create an HTML file named `Index` and paste the generated `Index.html` into it.
3. In Project Settings, enable the manifest file in the editor. Replace `appsscript.json` with the provided manifest.
4. In Script Properties, set `MATCH_LOG_SHEET_ID` to the existing log spreadsheet ID and `MATCH_LOG_ALLOWED_EMAILS` to the explicitly authorized staff Google emails, separated by commas. These values stay in Google and must never be committed to the public repository. A non-Gmail address must be associated with a Google account to use the tool.
5. Select `setupMatchLog` and Run from the bound editor. This creates a Decisions tab with headers only, preserves other tabs, and verifies an existing Decisions tab without rewriting records. Review the Google authorization prompts; it needs spreadsheet access and the signed-in email. It does not request Gmail or Drive-file access. The spreadsheet permission scope is broad, not restricted by Google to this one file, although the code opens only the configured log sheet.
6. Confirm the Decisions tab exists with its headers and no participant rows. Use test deployment for editor-only testing first. A deployment for ordinary staff must run as User accessing the web app, require a signed-in Google user, and keep the server-side exact email allowlist in place. The domain-only setting would exclude authorized external Google accounts, so the manifest uses ANYONE (signed-in), never ANYONE_ANONYMOUS. Everyone still needs access to the specific sheet. Do not deploy as the owner to bypass individual permissions.
7. Test with fictional identities: record with a required reason, reload and find the saved row, confirm assignment, make a correction, and verify earlier events remain. Test an authorized second staff account and an unauthorized account before using real data.
8. Before production, choose a separate approved deployment/version, confirm its access settings, and record the staff URL in the existing team folder/index. Review changes and obtain Cindy's approval before commits, pushes, PRs, or publication. Keep the prior working deployment available for rollback.

## Boundaries

Only identity, proposed mentor scores, weights, reason and decision status are persisted. Raw survey answers, bios, lived experiences and uploaded answer files are not saved by the log. Free text typed into the reason may contain sensitive information: keep it relevant to the decision. Scores are a snapshot of the staff page, not independent server recalculation or scientifically validated predictions.

Google Sheet editors can edit underlying records directly; append-only means the webpage preserves history, not that the sheet is tamper-proof. The schema checks detect changed headers, not every direct row edit. Google version history remains relevant for recovery. A scheduled backup and retention policy have not been configured.

The local tests simulate Apps Script services and browser controls. Actual Google authorization, storage readback, staff-account access and the deployed interface must be tested separately before completion is claimed.
